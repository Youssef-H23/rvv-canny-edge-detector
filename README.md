# Canny Edge Detection on RISC-V (RVV)

This repository contains the implementation of a Canny Edge Detection pipeline optimized for the RISC-V architecture, specifically leveraging the RISC-V Vector Extension (RVV 1.0). 

The project follows a "Host-Driven Development" workflow: the scalar baseline and unit tests are developed and verified natively on the host machine before being cross-compiled and tested on a RISC-V emulator (QEMU).

## 🛠️ Prerequisites & Environment

Before building, ensure your environment (e.g., WSL2 / Ubuntu 24.04) has the following dependencies installed:

1. **Host Compiler:** Standard `g++` (for native testing and verification).
2. **RISC-V Toolchain:** `riscv64-unknown-elf-g++` built from source with Vector extension support (`--with-arch=rv64gcv`).
3. **QEMU Emulator:** `qemu-riscv64` for executing RISC-V binaries on the host machine.
4. **GoogleTest:** Installed locally in your user directory (`~/.local/include` and `~/.local/lib`).

## 🚀 Build and Execution Guide

This project utilizes a dual-target `Makefile` to seamlessly switch between host-side debugging and RISC-V emulation. Run all commands from the root directory.

### 1. Host-Side Testing (Algorithm Verification)
To compile and run the GoogleTest suite natively on your machine:
```bash
make test
```
*Use this target constantly during development to verify that your C++ logic works perfectly before attempting cross-compilation.*



### 2. Running Natively on Host (Visual Check)
To compile and run the pipeline natively on your host machine for a quick execution and visual check:
```bash
make host_run
```


### 3. Cross-Compiling for RISC-V
To cross-compile the main application for the RISC-V architecture using the Scalar baseline or the Vector Extension:

*For Cross-Compiling the Scalar Pipeline
```bash
make canny_rv
```
*For Cross-Compiling the Custom RVV Intrinsics Pipeline
```bash
make canny_vector
```
*This uses your RISC-V toolchain to generate the `canny_pipeline.elf` or `canny_vector.elf` binary inside the `build/rv/` directory.*


### 4. Running on QEMU Emulator
To execute the cross-compiled RISC-V binaries via QEMU:

To run the Scalar Pipeline
```bash
make run
```
To run the Custom Vector Pipeline
```bash
make run_vector
```
*Note: The Makefile passes the `VLEN=128` parameter to QEMU by default, simulating a 128-bit vector register length. Do not hardcode this value in your C++ code!*


### 5. Vector Equivalence Testing
To run tests that validate your custom RVV vector implementation yields mathematically identical results compared to the scalar baseline across multiple hardware register sizes:
```bash
make vector_test
```
*This automatically builds and executes the vector test suite on QEMU sequentially forcing VLEN=128, VLEN=256, and VLEN=512 bits.*


### 6. Sweeping Vector Lengths (VLEN)
To prove the implementation is Vector Length Agnostic (VLA), you can run the executable across multiple hardware configurations automatically:
```bash
make sweep_VLEN
```
*This executes the RISC-V Vector binary on QEMU with VLEN set to 128, 256, and 512 bits consecutively.*




### 7. Sweeping Optimization Levels & Auto-Vectorization
To test the scalar pipeline across all standard GCC optimization levels ($O0$, $O1$, $O2$, $O3$, $Os$, $Ofast$) and dump compiler diagnostic reports:
```bash
make sweep_opt
```
*This executes the performance sweep, checks binary sizes, and saves the detailed auto-vectorization decision logs inside the `autovec_reports/` directory.*



### 8. LMUL Scaling Experiment
To profile the performance impact when altering the Vector Register Grouping factor (LMUL) to analyze the trade-off between register pressure and loop throughput:
```bash
make sweep_lmul
```

### 9. Post-Processing & Visual Utilities
To convert the processed raw image output or manipulate output frames:

Convert output/raw/*.raw artifacts into viewable PNGs
```bash
make show
```
Convert reference PNGs back into raw buffers for precise binary diffing
```bash
make convert

```


### 10. Filter & Norm Timing Comparisons
To benchmark Gaussian 2D-vs-separable convolution (scalar and RVV) and L1-vs-L2 magnitude norm timing, swept at -O2 and -O3:
```bash
make compare
```
*See "Separable Filter & L1 vs L2 Norm Comparison" below for the results and why a single optimization flag isn't enough here.*

### 11. Full Optimization Table
To build the scalar pipeline at every GCC optimization level plus the RVV pipeline (VLEN 128/256), and print a single per-stage timing + binary-size table covering all 7 Canny stages:
```bash
make opt_table
```
*Each cell is averaged over multiple QEMU runs of the same binary -- see `scripts/optimization_table.sh` for why that matters (QEMU's own run-to-run timing noise was observed to exceed 50% on a single invocation).*

### 12. Cleaning the Workspace
To remove all generated build artifacts, object files, binaries, and temporary directories:
```bash
make clean
```





## 📊 Scalar Pipeline Performance Sweep

Below are the detailed profiling results for the *Scalar Pipeline* executed across *100 iterations* using different GCC optimization flags ($O0$ to $Ofast$) on QEMU (VLEN=128).


| Canny Stage / Metric | O0 (No Opt) | O1 (Basic) | O2 (Moderate) | O3 (Aggressive) | Os (Size) | Ofast (Fastest) |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| *Stage 1: Gaussian Blur* | 10.0551 s | 3.7758 s | 3.0472 s | *1.0037 s* | 3.8172 s | 1.6852 s |
| *Stage 2: Sobel Gradients* | 3.9999 s | 8.0955 s | 1.4984 s | 0.2731 s | 2.0920 s | *0.2692 s* |
| *Stage 3a: Magnitude L1* | 0.6482 s | *0.4519 s* | 1.2092 s | 2.0031 s | 0.4717 s | 1.8362 s |
| *Stage 3b: Direction* | 0.3594 s | 0.2198 s | *0.2020 s* | 2.1755 s | 0.2474 s | 2.1848 s |
| *Stage 4: Non-Max Suppression* | 1.1275 s | 0.2822 s | 0.2748 s | 0.2769 s | 0.3032 s | *0.2743 s* |
| *Stage 5a: Double Threshold* | 0.1710 s | 0.1022 s | *0.0751 s* | 0.3343 s | 0.0956 s | 0.3223 s |
| *Stage 5b: Hysteresis Tracing* | 0.4370 s | 0.2925 s | 0.4645 s | 0.4656 s | *0.2894 s* | 0.4571 s |
| *Total Pure Pipeline Time* | *16.7981 s* | *13.2200 s* | *6.7713 s* | *6.5323 s* | *7.3165 s* | *7.0290 s* |
| *Binary Size (Bytes)* | 410,704 B | *404,232 B* | 404,672 B | 408,696 B | 404,392 B | 408,720 B |

### 🔍 Architectural Insights & Analysis

1. *The $O3$ Micro-Architectural Paradox:* While $O3$ drastically optimized the *Gaussian Blur* (down to 1.0037 s) and *Sobel* (down to 0.2731 s), a massive performance regression occurred in *Magnitude* and *Direction* stages (jumping up to over 2.0 s). This indicates that GCC's aggressive automatic loop unrolling and auto-vectorization backfired in these specific stages, likely causing severe *Register Spilling* or L1 Instruction Cache thrashing within the emulator. 
   
2. *Gaussian Blur Bottleneck Reduction:*
   The compiler scheduling and instruction-level parallelism under $O3$ achieved a massive *10x speedup* on Stage 1 compared to $O0$, showing that heavy coordinate mapping and stencil loops benefit the most from compiler branch optimization.

3. *Embedded Efficiency (Os flag):*
   The $Os$ flag successfully reduced the final binary size to *404,392 bytes* (nearly identical to $O1$), while retaining an impressive total execution time of 7.3165 s, making it the most balanced candidate for memory-constrained embedded environments.

4. *The $O1$ Sobel Anomaly:* Reproduced independently across multiple runs (see table below): Sobel jumps to its *worst* time at $O1$ (worse than even $O0$ in some runs), then drops sharply at $O2$/$O3$. Not noise -- a real artifact of GCC's $O1$ optimization pass ordering for this specific loop nest.

Generated with `make opt_table` (`scripts/optimization_table.sh`). Unlike the table above (total time for 100 iterations), this is **per-iteration milliseconds**, isolated per stage, including the three bonus stages (NMS, Double Threshold, Hysteresis) and both RVV VLEN configurations:

| Sobel Gx/Gy | 33.667ms | 87.476ms | 11.996ms | **2.195ms** | 19.355ms | 2.554ms | 14.921ms | 10.918ms |
| Magnitude | 5.193ms | 3.596ms | 11.944ms | 23.222ms | 3.770ms | 23.878ms | **5.114ms** | **4.226ms** |
| Direction | 3.061ms | 1.889ms | **1.785ms** | 24.015ms | 2.066ms | 27.506ms | 2.034ms | 2.091ms |
| Non-Max Suppr. | 11.784ms | 2.331ms | 2.329ms | **2.270ms** | 2.604ms | 2.565ms | 2.550ms | 2.734ms |
| Double Thresh. | 1.444ms | 0.883ms | **0.633ms** | 3.038ms | 0.821ms | 3.478ms | 0.671ms | 0.695ms |
| Hysteresis | 3.851ms | 2.646ms | 4.504ms | 4.372ms | **2.638ms** | 4.995ms | 5.073ms | 3.771ms |
| Binary size | 401.1KB | 394.8KB | 395.2KB | 399.1KB | 394.9KB | 399.1KB | 398.1KB | 398.1KB |

**Reading this table:**
- **Direction, NMS, Double Threshold, and Hysteresis have no RVV implementation** -- their RVV 128/256 numbers are the *same scalar code*, just timed inside the `-DUSE_RVV -O2` binary, which is why they land close to the `-O2` column (e.g. Direction: 1.785ms at `-O2` vs 2.034ms at RVV 128). This was a deliberate choice: profiling showed Gaussian + Sobel + Magnitude as the hotspots, and Amdahl's law says vectorizing an 8%-of-runtime stage like Direction isn't worth the effort.
- **RVV wins decisively for Magnitude** (beats every single scalar column, including `-O0`) -- this is the one stage where hand-written RVV intrinsics clearly outperform anything the compiler produces on its own.
- **RVV is slower than scalar `-O3` for Gaussian and Sobel.** We're reporting this honestly rather than hiding it: `-O3` auto-vectorizes Sobel's simple elementwise arithmetic effectively, and our hand-written RVV Gaussian/Sobel kernels carry strip-mining and widening overhead that doesn't pay off at this image size under QEMU's emulation. The win is visible against `-O0`/`-O1`/`-Os`, just not against `-O3`.
- **`-O3` regresses Magnitude and Direction** relative to `-O2` (Magnitude: 11.9ms → 23.2ms; Direction: 1.8ms → 24.0ms) while *helping* Gaussian/Sobel. `-fopt-info-vec-all` shows why: GCC's auto-vectorizer successfully vectorizes the simple Magnitude/Direction loops using masked, variable-length RVV instructions, but completely fails on the convolution loops ("loop nest containing two or more consecutive inner loops"). Convolutions get faster at `-O3` purely from inlining/scheduling with no vectorization tax; Magnitude/Direction pay for masked-vector instructions that are apparently expensive for QEMU to emulate, and come out behind plain `-O2` scalar code.
- Each cell is the average of independent QEMU process launches of the same binary -- run-to-run noise on a single launch was measured as high as ~50% during development, so don't over-read small differences between adjacent columns.

## 🪚 Separable Filter & L1 vs L2 Norm Comparison

Generated with `make compare` (`tests/comparisons.cpp`), answering the project guide's own "Deeper Idea" prompts in sections 2.2 and 2.4: does the separable Gaussian (1x5 + 5x1, 10 MACs/pixel) actually beat the full 5x5 2D convolution (25 MACs/pixel), and how much does L2's `sqrtf` cost over L1's integer abs+add? Swept at `-O2`/`-O3` since the answer changes with optimization level:

| Comparison | -O2 | -O3 |
| :--- | :---: | :---: |
| Gaussian 2D, scalar | 3.88 s | 2.42 s |
| Gaussian separable, scalar | 31.36 s (**0.12x** -- slower) | 18.89 s (**0.13x** -- slower) |
| Gaussian 2D, RVV | 6.25 s | 6.78 s |
| Gaussian separable, RVV | 5.04 s (**1.24x** faster) | 5.11 s (**1.33x** faster) |
| Magnitude L1, scalar | 2.09 s | 3.15 s |
| Magnitude L2, scalar | 2.25 s (1.08x slower) | 2.11 s (noisy -- see below) |

**The separable filter is *slower*, not faster, in scalar code -- by 5-8x.** Cutting MACs from 25 to 10 should help, but it doesn't, because of memory access pattern, exactly as the project guide hints. We isolated this directly: the vertical pass (reading the horizontal pass's int32 temp buffer column-wise, stride = width × 4 bytes) measured **~30x slower** than the horizontal pass (sequential byte reads) for the same number of kernel taps, in a controlled side-by-side timing. The separable RVV version *does* win (1.2-1.3x), because the vectorized loads amortize that strided cost differently. This is a genuine, counterintuitive, data-backed answer to "discuss why the separable version might or might not be faster on QEMU" -- not the textbook answer, but a real one.

**L1 vs L2 magnitude timing is noisy at `-O3`** because GCC's auto-vectorizer vectorizes the L1 loop (simple abs+add) but not L2 (`sqrtf` blocks it -- confirmed via `-fopt-info-vec-all`: "vectorized 2 loops" for L1, "vectorized 0 loops" for L2), which sometimes nearly closes the gap and sometimes doesn't depending on the run. At `-O2`, where neither vectorizes, the result is stable and matches intuition: L2 is consistently ~8-26% slower than L1 across repeated runs.

## 🔬 Disassembly Excerpts

From `riscv64-unknown-elf-objdump -d build/rv/canny_vector.elf`, confirming the RVV intrinsics in `src/canny_vector.cpp` actually compile to vector instructions (not silently falling back to scalar):

**Gaussian convolution's widen → multiply-accumulate → narrow chain** (`gaussian_blur_rvv`, one kernel-tap iteration):
```asm
vsetvli zero,zero,e8,m2,ta,ma   # set vl for 8-bit pixels, LMUL=2
vle8.v  v2,(a5)                  # load 8-bit pixel chunk
vwcvtu.x.x.v v4,v2                # widen u8 -> u16 (LMUL doubles: m2 -> m4)
vsetvli zero,zero,e16,m4,ta,ma  # switch vl/LMUL for the widened type
vwmaccu.vx v8,a3,v4               # widening multiply-accumulate: u16 x scalar -> u32 accumulator
...
vmul.vx v8,v8,t0                  # fixed-point normalize: sum * 240
vsrl.vi v8,v8,16                  # ... >> 16  (approximates / 273)
vnsrl.wi v8,v8,0                  # narrow u32 -> u16
vnsrl.wi v8,v8,0                  # narrow u16 -> u8
vse8.v  v8,(a5)                   # store final pixel
```

**Magnitude L1's vector reduction** (`compute_magnitude_l1_rvv`, finding the running global max):
```asm
vmax.vv    v8,v8,v12     # |gx| = max(gx, -gx)
vadd.vv    v4,v4,v8       # magnitude = |gx| + |gy|
vse16.v    v4,(a2)        # store this chunk's raw magnitudes
vredmaxu.vs v1,v4,v1      # reduction: fold chunk max into running max (seed = v1)
vmv.x.s    a1,v1          # extract the scalar max out of element 0
```
